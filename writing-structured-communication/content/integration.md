# 整合设计：跨模块的知识关系

> 一句话定位：把 20 个模块的知识连成一张网——概念对照、方法选择、全流程地图、错误诊断树与跨场景案例。

## A. 概念对照表

以下六组概念最容易被混淆。每组用「同一个案例」贯穿对照，帮助建立精确区分。

### A.1 论点 vs 论据

| | 论点（claim） | 论据（grounds/evidence） |
|---|---|---|
| 回答的问题 | 你认为什么？你主张什么？ | 你凭什么这么认为？ |
| 性质 | 待支持的判断，可被质疑 | 已掌握的事实、数据、观察 |
| 案例（示例情境，虚构） | 「应将客服系统迁移至新平台」 | 「旧平台月均故障 4.2 次，新平台试运行 3 个月零故障」 |
| 常见错误 | 把论据当论点重复堆砌，全文没有可争议的主张 | 论点只有情绪与立场（「必须支持国货」），拿不出论据 |
| 检查方法 | 能否写出「我认为……因为……」句式 | 删掉所有论据后，论点是否还站得住 |

关键点：论据本身不是论点。大量数据不等于论证——数据之间必须有推理规则连接到主张。详见 [模块 04](modules/module-04.html)。

### A.2 论证 vs 解释

| | 论证（argument） | 解释（explanation） |
|---|---|---|
| 目的 | 让读者接受一个**真假存疑**的主张 | 让读者理解一个**已被接受**的现象如何发生 |
| 读者起点 | 不知道/不同意结论 | 知道结论，不知道为什么 |
| 典型问句 | 「应不应该做？」 | 「为什么发生了？」 |
| 案例 | 「应迁移平台，因为故障率相差 5 倍」 | 「迁移后故障下降，是因为新平台有双活架构」 |
| 混淆后果 | 把已知事实当争议点论证，浪费篇幅且显得不诚恳 | 把争议结论当已知事实解释，掩盖了论证责任 |

实用规则：先判断结论在读者心中是否已定。未定 → 论证；已定 → 解释。详见 [模块 04](modules/module-04.html)、[模块 07](modules/module-07.html)。

### A.3 摘要 vs 执行摘要

| | 摘要（abstract/summary） | 执行摘要（executive summary） |
|---|---|---|
| 读者 | 需要了解全文内容的读者 | 需要据此做决策的管理者 |
| 内容 | 研究/文章的目的、方法、主要发现的浓缩 | 结论、建议、所需决策、成本与风险 |
| 能否独立阅读 | 通常可以 | 必须可以 |
| 是否包含行动要求 | 一般不包含 | 必须包含 |
| 常见错误 | 把执行摘要写成「本文分四章……」的目录式摘要 | 执行摘要里塞满方法细节，读者找不到要做什么决定 |

### A.4 结构修订 vs 语言校对

| | 结构修订（structural revision） | 语言校对（copyediting） |
|---|---|---|
| 操作对象 | 章节顺序、论证顺序、信息取舍、读者适配 | 句子、词语、标点、格式、错字 |
| 解决问题 | 「读者读不懂、找不到重点、结论不突出」 | 「句子歧义、用词不当、前后不一致」 |
| 成本量级 | 可能重写大半 | 逐句打磨 |
| 顺序 | **必须先做** | 结构定稿后才能做 |
| 常见错误 | 结构没定就逐句润色，改完发现整段要删 | 用润色掩盖结构问题——文字更顺了，问题更隐蔽了 |

### A.5 事实 vs 观点 vs 评价

| | 事实（fact） | 观点（opinion） | 评价（evaluation） |
|---|---|---|---|
| 定义 | 可独立验证的陈述 | 个人判断，无需普遍验证 | 依据标准的价值判断 |
| 案例 | 「该产品 2025 年销量为 12 万件」 | 「我觉得这款设计很土」 | 「按转化率标准，该设计低于行业基准」 |
| 检验 | 有来源、可复核 | 承认主观性即可 | 标准必须先亮出 |
| 危险写法 | 无来源的具体数字写成事实 | 观点伪装成「事实证明」 | 不说明标准的「明显更优」 |

### A.6 归纳顺序 vs 演绎顺序

| | 归纳顺序（inductive grouping） | 演绎顺序（deductive chain） |
|---|---|---|
| 逻辑方向 | 多个同类事实 → 归纳出的结论 | 大前提 + 小前提 → 必然结论 |
| 金字塔中的位置 | 横向：同组观点相互支持 | 纵向：上一层由下一层推出 |
| 适用 | 分组、归类、列举支撑 | 需要严格推导的论证 |
| 案例 | 「故障率、成本、兼容性三项均占优 → 建议迁移」 | 「所有高故障系统必须更换；该系统月均故障 4 次 → 必须更换」 |
| 风险 | 归纳结论可能过度概括 | 前提不成立则全盘皆错 |

## B. 方法选择指南

没有唯一正确的结构。根据四个维度选择：

| 文档目标 | 首选结构 | 关键动作 | 对应模块 |
|---|---|---|---|
| 推动决策 | 金字塔结构 + SCQA 开头，结论先行 | 先写执行摘要，后补论证 | [03](modules/module-03.html)、[08](modules/module-08.html) |
| 解释机制 | 任务/概念导向，先决知识优先 | 画概念依赖图，决定解释顺序 | [07](modules/module-07.html) |
| 论证立场 | Toulmin 模型 + 反方检验 | 先列最强反方，再组织回应 | [04](modules/module-04.html)、[10](modules/module-10.html) |
| 指导操作 | 任务导向步骤结构 | 每个步骤有动作+对象+预期结果 | [12](modules/module-12.html) |
| 汇报进展 | 现状-问题-影响-建议 | 事实与判断分区呈现 | [08](modules/module-08.html) |
| 建立信任 | 证据链 + 限制披露 | 来源可追溯，结论不超范围 | [09](modules/module-09.html)、[16](modules/module-16.html) |

时间受限时的优先级（按影响排序）：
1. 结论是否出现在读者最先读到的位置。
2. 每个主张是否有证据。
3. 读者行动要求是否明确（做什么、何时、要什么）。
4. 语言问题（最后处理）。

## C. 工作流地图：从问题到发布

```
阶段 1 任务分析（模块 01）
  界定任务 → 明确目的 → 读者分析 → 成功标准
        ↓
阶段 2 信息收集（模块 09、16）
  检索 → 来源评估 → 证据记录 → 缺口标注
        ↓
阶段 3 结构设计（模块 02、03、05）
  问题拆解 → MECE 分组 → 金字塔大纲 → 段落功能分配
        ↓
阶段 4 论证构建（模块 04、10）
  主张-证据-推理链 → 反方检验 → 限定条件
        ↓
阶段 5 起草（模块 06、07、11–14）
  按大纲成稿 → 段落展开 → 语言控制
        ↓
阶段 6 修订（模块 15）
  结构修订 → 论证审查 → 句子编辑 → 校对
        ↓
阶段 7 核查（模块 16）
  事实核查 → 引用核对 → 证据强度匹配
        ↓
阶段 8 视觉化（模块 17）
  图表选择 → 与结论对齐 → 可访问性检查
        ↓
阶段 9 发布与反馈（模块 19）
  版本记录 → 收集反馈 → 复盘入库
```

注意：这是循环而非直线。修订阶段发现论证缺口时，必须回到阶段 2 或 4，而不是在文字上打补丁。

## D. 错误诊断树

从症状倒推原因。每个症状列出高频根因与修复动作。

### D.1 读者说「看不懂」

- 结论没有前置，读者读完全文才知道你要说什么 → 改为结论先行（模块 03）
- 概念未定义或先决知识被跳过 → 补概念依赖检查（模块 07）
- 单句信息过载、修饰关系混乱 → 拆分句子（模块 06）
- 段落缺少主题句，读者抓不住每段功能 → 补主题句（模块 05）
- 术语未解释且中英混杂 → 建术语表并统一（模块 06、术语词典）

### D.2 读者说「结论不可信」

- 论据与主张之间缺推理规则 → 用 Toulmin 模型补全链条（模块 04）
- 证据是二手转述而非原始来源 → 回溯一手来源（模块 16）
- 相关关系被表述为因果 → 降级结论或补机制证据（模块 02、16）
- 只列支持证据，无反方检验 → 补反方与替代解释（模块 04、10）
- 统计被误读（基数、均值陷阱、选择性区间）→ 核对统计口径（模块 04、16）

### D.3 读者说「太长了」

- 把解释写成了论证，或反之 → 重新判断读者心中结论状态（模块 04/07）
- 同一信息在摘要、正文、附录重复 → 分层去重（模块 05、14）
- 收集了用不到的材料，「舍不得删」 → 按读者任务反向取舍（模块 01）
- 句子冗长但信息量低 → 名词化改写、删套话（模块 06）
- 篇幅超标但内容必要 → 拆分为正文 + 附录 + 分层阅读设计（模块 14）

### D.4 报告「无法推动决策」

- 没有明确行动建议，只有现象描述 → 补「建议-负责人-期限」三要素（模块 08）
- 建议与证据不对应 → 建立结论-证据对照表（模块 08）
- 风险与替代方案缺失，决策者不敢拍板 → 补选项比较与异议回应（模块 10）
- 读者错位：写给所有人等于没写给任何人 → 重做读者分析（模块 01）
- 缺少执行摘要，管理者没读完 → 补执行摘要（模块 14）

### D.5 文本「感觉不专业但说不上来」

- 事实、分析、假设、建议混在一起 → 四类信息分区标注（模块 08）
- 术语前后不一致 → 术语一致性检查（模块 12）
- 数字、日期、专有名词未核对 → 校对清单专项过一遍（模块 15）
- 语气不统一（时而口语时而公文） → 定语气基调并统一（模块 06）
- 图表与文字结论矛盾 → 图表-结论对齐检查（模块 17）

## E. 跨场景案例：同一材料的五种表达

**原始材料（示例情境，虚构）**：某零售团队连续三个季度客单价下降。内部数据显示，下降主要来自新客户首单金额走低；老客户复购与客单价稳定。市场部同期将投放从品牌广告转向效果广告，新客数量上升 20%，但新客留存率从 35% 降至 28%。竞品同期未投放加码。

**同一事实链的五种产出**：

| 产出 | 读者 | 结构 | 核心信息 | 对应模块 |
|---|---|---|---|---|
| 说明文 | 新入职同事 | 概念 → 数据 → 机制解释 | 「客单价下降的结构性原因」 | 07 |
| 分析报告 | 业务负责人 | SCQA → 原因分析 → 选项 → 建议 | 「投放结构变化导致新客质量下降，建议调整预算配比」 | 08 |
| 决策邮件 | 部门总监 | 结论先行 → 三条理由 → 需要的决策 | 「请批准将 30% 效果预算回投品牌广告」 | 11 |
| 说服性提案 | 有异议的市场部 | 共识 → 分歧 → 证据 → 反方回应 | 「在增长目标不变前提下修正投放结构」 | 10 |
| 演示大纲 | 管理层汇报 | 一页一观点，共 6 页 | 问题 → 数据 → 机制 → 选项 → 建议 → 下一步 | 17 |

注意五种表达的事实完全相同，但**论证责任**不同：邮件只要求读者做一个决定；提案必须处理反对意见；报告必须完整展示证据链。

## F. 核心原则与例外

| 原则 | 为什么成立 | 例外/边界 |
|---|---|---|
| 结论先行 | 管理者时间有限，先看结论再决定是否读细节 | 读者需要自己得出结论（教学、启发式讨论）；坏消息需先铺垫事实再给结论 |
| MECE 分组 | 减少重复与遗漏，降低认知负荷 | 复杂现实问题常无法无争议划分；粒度取决于读者任务而非绝对完整 |
| 简洁 | 降低理解成本 | 删掉限定条件会让结论失真；法律、安全场景宁可冗长 |
| 故事结构 | 提升记忆与动机 | 不能替代研究报告的精确性；事实完整性优先于戏剧性 |
| 图表辅助理解 | 视觉通道分担语言通道负荷 | 装饰性图表增加负荷；误导性坐标轴比没有图表更糟 |
| 任务导向步骤 | 读者要完成任务而非读懂文字 | 概念性内容按概念依赖组织，不按操作步骤 |
| AI 提速 | 在构思、草拟、审查环节显著提效 | 事实、引用、最终判断必须人工核验（模块 16、18） |

## G. 如何使用整合设计页

1. 遇到具体写作任务：先查 B 节选结构，再进入对应模块深读。
2. 文本出问题：按 D 节症状倒推根因，再进对应模块修。
3. 概念含糊：回 A 节对照表校准。
4. 建立全局观：读 C 节工作流，理解模块间依赖关系。
