# 模块 12 · 技术文档、操作指南与流程说明

> 一句话定位：本模块训练「让读者完成任务」的文档写作——以任务组织信息、以步骤承载操作、以验收标准闭环。

## A. 学习导航

**本模块解决什么问题**
技术文档的成败标准不是「写得清不清楚」，而是「读者能不能不求助他人就完成任务」。常见失败有六种：按功能菜单而非读者任务组织；步骤缺前置条件与预期结果，读者做到一半不知对错；术语前后不一致；异常情况缺失，一出错就卡死；参数与限制不写；文档与产品版本脱节，照着做反而做错。本模块给出对应的结构、写法与维护方法。

**学习目标**（完成后应能）：
1. 能区分用户指南、操作步骤、故障排查、FAQ、技术说明与参考文档，并按读者状态选择结构。
2. 能把一个操作任务拆解为可执行、可验证的原子步骤。
3. 能写全前置条件、输入、步骤、预期结果与异常情况五要素。
4. 能建立并执行术语一致性检查，区分功能准确与机制准确。
5. 能描述流程、参数、限制与依赖关系，并正确选用表格与警告。
6. 能设计一次文档可用性测试，并建立变更记录与版本维护机制。
7. 能产出一份结构完整、可实际执行的操作指南。

**前置知识**：[模块 03](../modules/module-03.html)（结构组织）、[模块 06](../modules/module-06.html)（清晰表达）、[模块 07](../modules/module-07.html)（说明文与知识解释）、[模块 11](../modules/module-11.html)（任务导向的沟通）。

**关键概念**（中英对照）：

| 中文 | 英文 | 一句话解释 |
|---|---|---|
| 任务导向 | task-oriented | 以读者要完成的任务为单位组织文档 |
| 操作步骤 | procedure | 按顺序执行的动作序列 |
| 故障排查 | troubleshooting | 从症状定位原因并恢复的结构化路径 |
| 前置条件 | prerequisites | 开始前必须满足的环境、权限与资源条件 |
| 预期结果 | expected result | 操作成功后应观察到的可验证状态 |
| 异常处理 | exception handling | 出错或分支时的替代路径 |
| 术语一致性 | terminology consistency | 同一概念在全文档使用同一称谓 |

| 变更记录 | changelog | 按版本记录文档改动的清单 |
| 最小可复现示例 | minimal reproducible example | 能独立运行、直指问题的最简示例 |
| 文档腐烂 | documentation rot | 文档随产品演进而失效的过程 |

## B. 系统化知识讲解

### B.1 技术写作的目标、读者与文档类型

**目标：让读者完成任务（task-oriented）**
技术写作的产出不是「信息」，而是「读者行为的改变」——读者读完能完成一个操作、排查一个故障、做出一个配置决策。ISO/IEC/IEEE 26512:2018 把用户文档视为系统交付物的组成部分，要求文档依据用户的任务与特征来规划、开发与维护（来源 26，标准/规范性文件）。这意味着文档质量可以用「任务完成率」衡量，而不只是「文字质量」。

**三类信息，三种组织方式**
任何技术文档的内容都可归入三类，混在一起写是结构混乱的主因：

| 信息类型 | 回答的问题 | 组织方式 |
|---|---|---|
| 任务（task） | 怎么做到 X | 按步骤，编号列表 |
| 概念（concept） | X 是什么、为什么 | 按定义—机制—边界 |
| 参考（reference） | 参数/字段/命令的确切含义 | 按字母或逻辑序的表格 |

**读者分层**
同一产品的读者分三层：新手需要步骤与预期结果；熟手需要快速定位与筛选条件；专家需要参数、限制与内部机制。一份文档服务所有层次的常见办法是分层导航：正文按新手路径写，参考部分独立成表，专家直达。

**文档类型矩阵**

| 文档类型 | 读者状态 | 核心信息需求 | 结构 |
|---|---|---|---|
| 用户指南 | 不知道能做什么 | 我能用这个产品完成什么 | 按目标场景分章 |
| 操作步骤 | 知道目标，不知怎么做 | 第一步是什么、怎么算对 | 五要素步骤（B.3） |
| 故障排查 | 遇到问题，有症状 | 我的症状对应哪个原因 | 症状—原因—措施表 |
| FAQ | 有具体疑问 | 直接答案 | 问句即标题 |
| 技术说明 | 需要理解机制 | 原理与边界 | 概念结构 |
| 参考文档 | 查确切定义 | 准确、完整、可检索 | 表格化条目 |

### B.2 任务导向的结构设计

**以任务为单位切分**
读者带着任务来：「我要导出上月报表」「我要排查为什么任务没跑」。文档的章节标题应该是任务名（「导出季度报表」），而不是功能名（「报表中心介绍」）。功能目录是产品的地图，任务目录才是读者的路径。

**步骤的原子性（规范性建议）**
一条步骤只含一个可观察动作。判断方法：把步骤交给一个不了解背景的人，他能否不提问地执行？「登录后台，进入报表页，点击导出，选择 CSV 格式，确认」应拆为五条，因为任何一步失败都需要单独定位。主流风格指南对步骤写作的一致建议是：一句一动作、用命令式、用第二人称（来源 19、20，规范性建议）。

**用认知负荷原理排布信息（经验证据）**
Sweller 的认知负荷理论指出，工作记忆容量有限，教学设计应减少与任务无关的「外在负荷」（来源 5，经验证据）；Paas 等人发展了认知负荷的测量方法，使「读者有多累」成为可检验的问题（来源 6，经验证据）；Mayer 的多媒体学习研究则给出图文并置、分段呈现等降低负荷的原则（来源 7，经验证据）。落到文档写作：
1. 步骤前后不放无关背景，背景放操作前的「关于本任务」小节；
2. 图与说明文字邻近，不让读者在图和文之间来回翻；
3. 长任务分阶段，每阶段有检查点；
4. 同一屏幕内不混排两种信息类型（步骤里插概念讲解）。

### B.3 操作步骤的完整结构：前置条件、输入、步骤、预期结果与异常

**五要素模板**

| 要素 | 内容 | 漏写的后果 |
|---|---|---|
| 前置条件 | 权限、环境、版本、数据状态 | 读者做到第 3 步才发现没权限 |
| 输入 | 需要读者准备的文件、参数、信息 | 读者边做边找，中断 |
| 步骤 | 编号动作序列，一条一动作 | 步骤粘连，失败无法定位 |
| 预期结果 | 成功后看到什么（界面状态、输出、消息） | 读者不知道对错，不敢继续 |
| 异常 | 常见错误现象、原因与对策 | 一出错就卡死，只能求助 |

**为什么预期结果是刚需**
没有预期结果的步骤是「盲操作」：读者完成了动作，却无法验证状态，也不敢继续。预期结果要写成可观察的判据（「页面右上角出现绿色提示『导出成功』，文件自动下载」），而不是形容词（「导出成功」）。

**分支与异常的显式化**
两种写法：① 内嵌分支——「若导出量超过 10 万行，先执行『分批导出』；否则继续下一步」；② 异常表——现象、可能原因、处理动作三列。前者用于决策点，后者用于故障定位。二者不可互相替代：把异常塞进步骤会破坏步骤的线性，把决策点塞进异常表会让读者漏读。

**可执行步骤：写一条合格的步骤**
1. 确认动词是命令式、可观察（点击/输入/勾选/等待）；
2. 主语是「你」（第二人称），界面元素加引号与准确名称；
3. 一条一动作，超过两个动宾结构就拆条；
4. 需要等待的写明等待对象（「等待状态变为『已完成』，通常 1–3 分钟」）；
5. 不可逆操作前加警告（B.6）。

### B.4 术语一致性与技术准确性

**一词一义，一义一词**
同一概念在全文档用同一称谓；同一称谓只指一个概念。常见错误是「同义词替换」——为了行文华丽在「删除、清除、移除、清掉」之间切换，读者无法确定是否指同一个按钮。操作文档中，界面元素的名称必须与产品 UI 逐字一致，包括大小写与标点。

**术语管理三件套**
1. 术语表：全文档统一入口，含中英对照与定义；
2. 首现定义：术语第一次出现时给出简短定义（[模块 07](../modules/module-07.html) 的方法）；
3. 一致性检查：完稿后全文搜索每个术语的别称，逐一判决。

**技术准确性的两个层次**
- 功能准确：描述产品实际行为（点击后发生什么）——面向用户文档的底线。
- 机制准确：描述内部原理（为什么这样）——技术说明的需要。
二者的风险不同：功能不准确会直接导致操作失败；机制不准确导致误解但可能不影响操作。写作优先级上，用户文档先保证功能准确，再追求机制准确；把机制假设写成事实（「系统会实时同步」而实际是五分钟延迟）是典型的越界。

**准确性的维护责任**
术语与行为会随产品变更。准确不是一次写对，而是建立「产品变更 → 文档复审」的触发机制（B.7）。

### B.5 描述流程、参数、限制与依赖

**流程描述的三种形态**
线性流程（步骤列表）、分支流程（判定点 + 路径表）、循环/迭代流程（阶段 + 退出条件）。文字步骤承载「做什么」，流程图承载「全局结构」——两者的分工来自图形感知研究：表格适合精确值查询，图形适合展示关系与趋势（来源 9，经验证据；Tufte 的数据墨水原则进一步强调图形应去掉无关装饰，来源 8，理论/经验证据）。实务规则：流程全貌用一张简图，每步细节用文字，不让图承担精确参数。

**参数表的设计**
列：参数名、类型、必选/可选、默认值、取值范围、说明。规则：单位放进表头（「超时（秒）」而非「超时」列里写「30 秒」）；默认值明确写出；取值约束写边界（「1–100，含端点」）而非「建议合理范围」。

**限制与依赖必须显式**
三类必须写进文档的信息：
1. 环境依赖：操作系统、浏览器版本、网络要求；
2. 版本依赖：功能自哪个版本起可用、在哪个版本有已知问题；
3. 配额与权限：行数上限、频率限制、所需角色。
读者失败最多的场景不是「不会操作」，而是「撞上未写明的限制」。限制写在任务开头（前置条件区），不要藏在文末附录。

### B.6 代码示例、表格、警告与注释

**代码示例四原则**
1. 最小可运行：能原样复制执行，不依赖读者本地特殊环境；
2. 上下文完整：语言、版本、依赖声明齐全；
3. 关键行有注释：注释解释「为什么」，不解释「是什么」；
4. 可验证：示例应附带预期输出，读者能自行判断成败。

**表格的用法**
表格适合「多对象 × 多属性」的精确查询（参数表、症状—原因表、版本对照表）。表头写清单位与条件；行序稳定（逻辑序或字母序），不要每次发布重排行序——读者会按位置记忆。

**警告分级与位置**
统一四级：**危险**（不可逆的人身或数据损失）、**警告**（可能导致数据丢失或服务中断）、**注意**（常见陷阱）、**提示**（效率建议）。三条规则：
1. 位置在危险动作之前，不要放在步骤之后；
2. 格式全文统一（同一图标/同一颜色/同一标题词）；
3. 每条警告给「后果 + 规避动作」，不写空泛的「请小心」。

**注释与标注**
示例中的注释只保留两类信息：非显然的约束（「此处必须等待同步完成，否则读到旧值」）和读者可能困惑的反直觉点。逐行翻译代码的注释是噪音——代码本身已经说明它做什么。

### B.7 文档可用性测试与维护

**可用性测试（usability testing）**
Nielsen Norman Group 的方法论文献指出，可用性测试的核心是观察真实用户执行代表性任务并记录卡点（来源 29，经验证据/方法论文献）。最小可行版本：
1. 找 3–5 名目标读者（新手优先，他们最暴露问题）；
2. 给任务不给步骤：「请用这份文档完成季度报表导出」；
3. 请读者出声思考（think aloud），记录卡住的位置、时长与求助行为；
4. 统计：无提示完成率、首次尝试成功率、平均用时、卡点分布；
5. 修订后对同一任务复测。

注意边界：小样本测试用于发现问题，不用于证明「文档好用」——后者需要更大范围的抽样。

**维护三机制**
1. 变更记录（changelog）：按版本列出「改了什么、为什么改、影响哪些任务」；
2. 版本标注：每份文档标注适用的产品版本，读者可判断是否适用于自己的环境；
3. 复审与反馈：固定复审周期（随产品发布节奏）+ 每页一个反馈入口（「这篇指南解决你的问题了吗」）。

**文档腐烂（documentation rot）**
产品每周迭代，文档每季度才修一次，腐烂必然发生。对策不是「写得慢一点」，而是把文档当作产品的一部分纳入发布流程：功能变更的验收标准里包含「相关文档已更新」。

### B.8 产出：一份结构完整的操作指南

操作指南的骨架（即 C 节演示的交付物形态）：

1. 标题：任务名（动词开头，如「导出季度报表」）；
2. 概述：这个任务帮读者达成什么目标，一段说完；
3. 前置条件：权限、环境、版本、数据状态；
4. 输入：需要准备的文件、参数、信息；
5. 操作步骤：编号，一条一动作，每步后可附预期结果；
6. 预期结果与验证：整任务完成后的可观察状态；
7. 异常与故障排查：现象—原因—措施表；
8. 相关任务与参考：链接到相邻任务、参数表、术语表；
9. 变更记录：版本、日期、改动摘要。

## C. 逐步演示

**案例：为虚构 SaaS 产品「灯塔分析」写「导出季度报表」操作指南**（示例情境，虚构；产品、界面、数据均为教学虚构）

### 1. 原始材料/问题输入
产品经理的口述需求与一份旧文档草稿：

「我们报表模块改版了，你写个导出指南吧。旧文档是这样的：『进入报表中心，选择时间范围，点击导出按钮，选择格式，等待下载完成。如需筛选维度请先在筛选器设置。导出量大时可能较慢，请耐心等待。如遇问题请联系技术支持。』」

### 2. 初始判断
- 没有任务定位：标题应是任务名，而非模块名；
- 五要素缺三：无前置条件（权限、版本）、无输入（时间范围怎么定）、无预期结果（成功长什么样）；
- 步骤粘连：「选择时间范围，点击导出，选择格式」是一条还是三条？读者无法对照排查；
- 「可能较慢」不是可验证信息：多久算慢、超过多久算异常？
- 「请联系技术支持」把文档的责任推给了别人——文档应至少覆盖最常见异常。

### 3. 分析过程

**读者分析**：主要读者是运营专员（新手—熟手之间），任务频率每月一次；痛点是「选错时间范围导致数据对不上」和「不知道导出成功没有」。专家读者（数据分析师）需要字段口径，放参考链接。

**任务分解**：把「导出」拆为四个子任务——确认权限与版本、设定时间范围与维度、执行导出、验证结果。每个子任务独立可验证。

**认知负荷控制（B.2）**：旧文档把筛选器说明混在步骤里，改为前置输入区；等待时间给区间与判据；界面元素名称加引号与 UI 逐字一致。

**术语清单**：导出 / 下载 / 生成三个词旧文档混用——统一为：产品内的动作叫「导出」，浏览器行为叫「下载」，「生成」指后台计算过程，三者不得互换。

### 4. 结构设计过程
按 B.8 骨架组织；异常表按「现象—原因—措施」三列设计；参数（时间范围、格式）收进输入区的小表；警告放在不可逆操作前（本任务无不可逆操作，但保留「注意」级提示：导出文件含脱敏前的明细数据，分享前需确认接收方权限）。

### 5. 修改前/后对照表

### 6. 最终版本（操作指南全文）

**导出季度报表（v2.4 起适用）**
概述：本任务帮你在「灯塔分析」中导出指定自然季度的成交报表，用于月度经营复盘。全程约 5 分钟，其中后台生成通常 1–3 分钟。

前置条件：
- 拥有「报表查看」及以上权限（权限不足时导出按钮为灰色）；
- 产品版本 ≥ 2.4（版本号见页面左下角）；
- 已确认当季数据同步完成（「数据中心」状态显示「已同步」）。

输入：

| 输入项 | 说明 |
|---|---|
| 时间范围 | 自然季度，如 Q2 = 4 月 1 日–6 月 30 日；跨季请分两次导出 |
| 维度 | 可选，渠道 / 品类 / 地区，最多同时选 3 个 |
| 格式 | CSV（通用）或 XLSX（含公式列） |

操作步骤：
1. 登录「灯塔分析」，点击左侧导航「报表中心」。
2. 点击顶部标签「成交报表」。（预期：页面展示本季度默认数据。）
3. 在右上角「时间范围」选择目标季度，点击「应用」。（预期：表格刷新，标题显示所选季度。）
4. 如需按维度拆分，在「维度」面板勾选目标维度。（预期：表格出现对应分组的汇总列。）
5. 点击「导出」，在弹窗中选择格式，点击「确认」。（预期：页面出现提示「任务已创建」，状态变为「生成中」。）
6. 等待状态变为「已完成」，浏览器自动下载文件。（预期：下载栏出现以「成交报表_季度_日期」命名的文件。）

验证清单（完成后逐项确认）：
- 文件名中的季度与目标季度一致；
- 行数与页面表格显示的行数一致（页面右上角显示总行数）；
- 首行字段名与字段说明表一致（见「成交报表字段说明」）。

异常与故障排查：

| 现象 | 可能原因 | 处理动作 |
|---|---|---|
| 导出按钮为灰色 | 权限不足 | 联系空间管理员开通「报表查看」 |
| 状态超过 10 分钟仍为「生成中」 | 数据量超过 100 万行 | 缩小时间范围或减少维度后重试 |
| 下载文件打开乱码 | 选择了 CSV 但用 Excel 直接打开 | 用 Excel「数据—自文本/CSV」导入，选 UTF-8 |
| 文件行数与页面不一致 | 页面默认只显示前 1,000 行 | 以文件为准，页面行数为预览值 |

注意：导出文件包含脱敏前的客户明细，分享前请确认接收方权限。

相关任务与参考：「分批导出的设置」「成交报表字段说明」「权限申请流程」。
变更记录：v1.2（示例日期）按 v2.4 改版重写，新增前置条件与异常表；v1.1（示例日期）修正格式说明。

### 7. 结果评估

可用性测试模拟（示例）：请两名新手按本文档执行。记录到的卡点：第 3 步「应用」按钮被忽略（两名读者都先改了维度再找应用）——修订方向：把「应用」写进步骤标题「选择季度并点击『应用』」。第 6 步浏览器拦截下载导致读者以为失败——修订方向：预期结果中补一句「若浏览器拦截下载，请允许站点下载」。这就是可用性测试的价值：作者认为显然的一步，读者视角是断点。

## D. 正例、反例与边界案例

| 类型 | 案例 | 判断依据 |
|---|---|---|
| 正确应用 | 步骤一条一动作，每步附预期状态，任务后附验证清单 | 读者可自验证（B.3）；失败可定位到步 |
| 正确应用 | 异常表按「现象—原因—措施」组织，与步骤分离 | 排查路径与操作路径分离（B.3 分支显式化） |
| 常见错误 | 「等待生成完成（可能需要几分钟）」 | 不可验证；应给区间与超时处理（B.3） |
| 常见错误 | 术语在「删除/清除/移除」间替换 | 违反一词一义（B.4） |
| 常见错误 | 把产品机制假设写成事实（「数据实时同步」） | 功能准确优先于机制准确；假设须标注（B.4） |
| 容易混淆 | 与 FAQ 对照：FAQ 是「疑问驱动」的短答案，操作指南是「任务驱动」的完整路径；同一信息两种组织 | 读者状态不同：有疑问 vs 有任务 |
| 容易混淆 | 与[模块 07](../modules/module-07.html) 说明文对照：说明文解释概念，操作指南改变行为；写反了读者就无所适从 | 目的不同：理解 vs 完成 |
| 适用边界 | 探索型任务（调研、创意）写成严格步骤 | 步骤的前提是路径确定；不确定领域给框架不给步骤 |
| 适用边界 | 面向专家的内部工具写新手式手把手 | 过度分步增加外在负荷（B.2）；专家要参考与限制 |

## E. 实战练习

### E.1 基础概念判断（2-3 小题）

1. 判断正误：「操作指南写得越详细越好，每个按钮都解释一遍最安全。」
2. 「点击导出后，系统会在后台处理，处理完成后会通知您」——这句话作为「预期结果」缺什么？
3. 下列哪项属于「限制」而非「步骤」？A.「点击右上角设置」 B.「单次导出上限 100 万行」 C.「选择 CSV 格式」

### E.2 方法应用

**任务**：选一个你熟悉的产品操作，按五要素模板写一份 300 字操作指南。
**输入材料**：你熟悉的产品（软件、设备、实验流程均可）。
**完成要求**：前置条件、输入、步骤（≥4 条，一条一动作）、预期结果、异常（≥2 条）五要素齐全。
**评价标准**：每条步骤只含一个可观察动作；预期结果可验证；异常给处理动作而非只给原因。

### E.3 问题诊断

**任务**：诊断一段步骤的问题并给出改法。
**输入材料**：一段步骤（示例情境，虚构）：
「进入后台，在设置里找到推送选项，按需填写参数后保存，如果保存失败可能是网络问题或者参数不对，可以检查网络或修改参数后重试，还是不行就找管理员。」
**完成要求**：指出至少 5 处问题，每处给类型与改法。
**评价标准**：覆盖原子性、界面名称、预期结果、异常定位、责任边界五类中至少四类。

### E.4 文本修改

**任务**：把模糊的等待说明改写为可验证表述。
**输入材料**：一句模糊表述：「数据同步需要一段时间，请稍候，不要重复操作。」
**完成要求**：改写为可验证的等待说明 + 异常处理（80 字内）。
**评价标准**：有等待判据（看到什么算完成）、有超时阈值、有重复操作的后果说明。

### E.5 综合产出

**任务**：产出一份完整操作指南（800–1,200 字）。
**输入材料**：自选真实场景，或使用 C 节「灯塔分析」延续情境（标注虚构）。
**完成要求**：按 B.8 九段骨架；含参数表或输入表；≥6 条编号步骤；≥3 条异常；术语表（≥5 条）；变更记录；版本标注。
**评价标准**（评分维度）：任务完成度（五要素）30 / 步骤原子性与可验证性 20 / 术语一致性 15 / 异常覆盖 15 / 结构与可维护性（版本、变更记录）10 / 简洁度 10。

<details markdown="1">
<summary>参考答案与解析</summary>

**E.1**
1. 错误。超出任务需要的细节增加外在认知负荷（来源 5、7，经验证据），并把关键步骤淹没。详略的标准是读者完成任务所需，按钮级解释属于参考文档的职责，用链接分流。
2. 缺三样：可观察的判据（状态变成什么、通知长什么样）、时间判据（通常多久、超过多久算异常）、失败路径（一直不通知怎么办）。没有这三样，读者无法自行判断该继续等待还是该排查。
3. B。A 和 C 是读者执行的动作；B 是系统边界，属于必须在前置条件或限制区声明的信息（B.5）。

**E.2**（开放式）评分维度：五要素齐全；步骤原子性；预期结果可观察。常见扣分点：步骤里混入解释性文字（「点击 X，这个功能很强大」）、预期结果写成「成功」二字、异常只写原因不写动作。

**E.3** 问题清单（示例）：①「设置里找到推送选项」路径不可执行——菜单层级与准确名称缺失（界面元素须与 UI 逐字一致）；②「按需填写参数」——哪些参数、格式、范围全部缺失，读者无法准备输入；③ 无预期结果——保存成功长什么样没写；④「可能是网络问题或者参数不对」——异常未定位，把两个原因并列丢给读者，应拆成现象—原因—措施行；⑤「还是不行就找管理员」——未写升级前应收集什么信息（报错截图、参数值），管理员无法高效介入；⑥ 整段无版本与适用范围声明。

**E.4**（示例改写）「等待顶部状态变为『已同步』（通常 1–3 分钟）。超过 10 分钟未完成请刷新页面重试；同步期间重复提交会导致任务重复创建，请在状态变化前不要再次点击『同步』。」判断要点：等待判据（状态文案）、超时阈值、重复操作后果三者齐全。

**E.5**（开放式）按六维度评分。提示：术语表不是摆设——写完全文后做一次「别称搜索」；变更记录至少含版本号、日期、改动摘要三列；虚构产品必须标注「示例情境，虚构」。
</details>

## F. 复盘与知识巩固

**核心知识总结**
1. 技术文档的质量标准是任务完成率，不是文字质量；内容分任务/概念/参考三类，混写即混乱。
2. 章节标题用任务名不用功能名；步骤一条一动作、命令式、第二人称。
3. 五要素（前置条件、输入、步骤、预期结果、异常）是操作文档的最小完整结构；预期结果必须可观察。
4. 术语一词一义；功能准确优先于机制准确；机制假设必须标注。
5. 限制、依赖、配额写在任务开头；参数表单位进表头、边界写清楚。
6. 警告分四级、放危险动作之前、每条含后果与规避。
7. 可用性测试看无提示完成率与卡点；文档随产品版本维护，腐烂靠发布流程治理。

**必须掌握的概念清单**
任务导向、五要素（前置条件/输入/步骤/预期结果/异常）、术语一致性、认知负荷、可用性测试、变更记录、文档腐烂、最小可复现示例。

**常见错误检查表**
- [ ] 章节按产品功能菜单组织，而非按读者任务组织
- [ ] 步骤一条包含多个动作，失败无法定位
- [ ] 无前置条件，读者中途撞权限墙
- [ ] 预期结果写成形容词，不可观察
- [ ] 等待时间无判据、无超时阈值
- [ ] 同一概念多个称谓；界面名称与 UI 不一致
- [ ] 参数表缺单位、缺默认值、缺边界
- [ ] 异常只列原因不给处理动作
- [ ] 警告放在危险动作之后
- [ ] 文档无版本标注、无变更记录

**自我评估题**
1. 为什么「按任务组织」比「按功能组织」更能降低读者的认知负荷？请结合读者到达文档时的状态说明。
2. 预期结果为什么必须是可观察判据而非「成功」这类状态词？不可观察的预期结果会引发什么后果？
3. 功能准确与机制准确的优先级差异是什么？什么情况下可以把机制假设写进用户文档？
4. 小样本可用性测试能证明文档「好用」吗？它能证明什么？不能证明什么？
5. 「文档腐烂」的根因是什么？为什么把文档纳入产品发布流程比「安排人定期改」更有效？

<details markdown="1">
<summary>自我评估题参考答案</summary>

1. 读者到达文档时带着任务（「我要做 X」），其注意力和工作记忆都服务于完成任务；按功能组织的文档要求读者先做一次「功能 → 任务」的映射，这次映射本身就是额外负荷，且新手常常映射失败。按任务组织把读者直接放到路径起点，符合任务导向原则（B.1、B.2；认知负荷依据见来源 5、7）。
2. 不可观察的预期结果让读者无法验证状态，后果是「不敢继续」与「错了不知道」——要么停滞，要么带着错误结果往下做，后者更危险。可观察判据（界面文案、文件命名、行数）让验证成为读者可独立执行的子任务。
3. 用户文档优先功能准确（行为描述错误会直接导致操作失败）；机制准确服务于理解与排障。机制假设（如同步延迟、缓存策略）只有在标注为「设计如此」并给出可观察证据时可以写入，且不能替代功能描述；未标注的机制假设就是文档中的幻觉风险点（[模块 16](../modules/module-16.html)）。
4. 不能。小样本（3–5 人）测试用于发现问题——卡点、断点、误解位置，效度来自「真实执行 + 出声思考」，不来自样本量。要证明「好用」需要覆盖目标读者分布与任务抽样的量化研究。二者的混淆会导致团队用五个人的通过率宣称文档质量（来源 29 的方法边界）。
5. 根因是变更速率不对称：产品持续迭代，文档靠人工记忆维护，没有触发机制。「纳入发布流程」把文档更新变成功能上线的验收项之一，让变更自动触发文档复审；靠自觉的定期维护则每次都要重新发现「什么变了」，成本高且必漏。
</details>

## H. 自测与验收标准

- [ ] 能把任意一份现有文档的内容标注为任务/概念/参考三类，并指出混写位置。
- [ ] 写出的操作指南五要素齐全，且预期结果全部为可观察判据。
- [ ] 写出的每条步骤只含一个可观察动作，动词为命令式、主语为第二人称。
- [ ] 能对一份 1,000 字文档完成术语一致性检查，输出别称清单并统一。
- [ ] 能写出含单位、默认值、边界的参数表，并把限制放进前置条件区。
- [ ] 能按四级警告规范标注一条危险操作，位置在该动作之前。
- [ ] 能设计并执行一次三人小样本可用性测试，输出卡点记录与修订清单。
- [ ] 产出的指南含版本标注与变更记录，能说明下一次产品变更时哪些段落需要复审。
